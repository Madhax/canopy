# 03 — Security: Custody, Least Privilege, Revocation, Audit

**Series:** [Connector Governance](README.md) · **Prev:** [02-scoping-and-grants.md](02-scoping-and-grants.md) · **Next:** [04-operations.md](04-operations.md)

This is the connector **delta** against `docs/actuation/threat-model.md`'s v1 trusted-local posture, not a restatement. Today's model defends a closed loop: agents hold only a revocable run token, secrets exist only for the Model Gateway, no sandbox has general egress. Connectors change one thing — for the first time, agent-directed actions carry **real external credentials against real external state**. The governing principle carries over unchanged from `agent-envelope.md` §3: *scope is enforced by construction, never by model judgment*. Every mitigation below names its enforcement point — **catalog** (grant definitions + readiness checks), **envelope** (resolution, tier derivation), **runtime** (adapter, generated session config), or **server** (control plane: Tool Proxy, Secret Store, gates, ledger).

## 1. Threat-model delta

| # | Threat | Attack path | Mitigation (enforcement point) |
|---|---|---|---|
| **C-1** | **Credential exfiltration** by a prompt-injected agent | Injected text (e.g. a GitHub issue body) tells the agent to print or exfiltrate its token | Never happens because the agent never has one: all connector credentials are proxy-held (**server**) — plaintext exists only in control-plane memory during a call. Egress stays control-plane-only at every tier (envelope §5), so even a fully jailbroken agent has no route out. The Tool Proxy scrubs known secret patterns from connector responses before they reach the agent (**server**). The one standing exception — `cli-runtime.md` §8's readable OAuth config dir — is a documented, waived debt for the *model* credential and is **never extended to connectors** (§2). |
| **C-2** | **Scope escalation** — a grant used beyond its assignment's intent | An agent with `docs.repo.write` pushes unrelated branches, opens PRs on other repos, merges its own work | The five enforcement layers (envelope §3.3) plus mandatory first-class connector params — repo fixed by the instance, branch/path/channel/method allowlists per grant — checked per call at the proxy (**server**), not just compiled into session config (**runtime**). Merge is governed and, in the worked example, not even enabled (02 §6). Assignment-scoped additions expire with the assignment (envelope §3.2). Upstream credential ceilings (§3) mean even a proxy bug cannot exceed what the credential permits. |
| **C-3** | **Cross-org leakage** through a shared instance | Two orgs share one PAT or one warm MCP server process; org A reads org B's repos | Hard rule: **instances and credentials are org-scoped, never shared** — Secret Store bindings keyed by org (**server**); actuation refuses a grant whose credential binding belongs to another org (**envelope**, specializing `GRANT_CREDENTIAL_UNBOUND`). One upstream server process/connection per org, no shared warm state (**server** — enforcing what envelope §3.6 already declares: "operator-configured, org-scoped"). ToolEvents carry the org id, so cross-org access would be visible even if a bug allowed it. Honest caveat in §5's tenancy row: v1 shares one process and DB across orgs (`threat-model.md` non-defense) — credential isolation is real now; process isolation lands with the hosting preconditions. |
| **C-4** | **Malicious / compromised MCP server** — description injection, rug-pulls, poisoned results | A registered server's `tools/list` carries injected instructions, or swaps a tool's behavior post-approval | The curation rule verbatim (envelope §3.6): registration creates no grants; `GRANT_UNCURATED` blocks uncurated tools. Plus **schema pinning** (01 §5): hash of name+schema+description recorded at curation; drift on a granted tool fails closed per call (`GRANT_SCHEMA_DRIFT`, **catalog + server**) until re-curated. Agents see the curated grant's description, never the server's raw text (**runtime**). Results are untrusted input — see C-6. |
| **C-5** | **Supply-chain risk in packs** — a community pack ships an over-broad or malicious definition | An imported pack declares `riskClass: read` for something that writes, or points at an attacker endpoint | Packs are signed and version-pinned (**catalog**); import is an approval-gated operator act with a rendered diff of every grant's `riskClass`, `governedActions`, executor, and params (**server + UI**, 04 §3). A pack's risk assignments are advisory until the operator confirms them — the curation rule applies to imports exactly as to hand-registration. Executor endpoints resolve only to operator-registered instances, never to URLs the pack supplies (**server**). |
| **C-6** | **Inbound prompt injection via connector content** (the input half; C-1 is the output half) | O2 ingests issues on a cadence (`org-roadmap.md` §O2); issue bodies, PR comments, Slack messages are attacker-authored text delivered into a session | Accept that injection *will* land, and bound it: connector-sourced text is materialized as **data artifacts in `brief/`, never appended to charter instructions** (**runtime**, intake step — `cli-runtime.md` §1); every outward-visible action is governed while trust is low, so an injected agent can propose but not publish (**server**: ApprovalGate); provenance tags on connector-sourced artifacts show gate owners what the agent was reading (**server**). Blast radius stays the grant set, no egress, recursion boundary intact. |
| **C-7** | **Exfiltration through legitimate writes** | An injected agent with `docs.repo.write` pushes another workspace's contents to a public branch | Workspace isolation is absolute (invariant 2) — an agent can only leak *its own* workspace. Governed outward writes (**catalog + server**), per-grant target allowlists (C-2), and ToolEvents recording a params hash + payload size per write (**server**) make bulk exfiltration anomalous and attributable. |

## 2. Secret custody — write-only by construction

**Where secrets live.** The existing Secret Store (**server**): Fernet-encrypted at rest, write-only operator API — create/rotate/delete return metadata only (`threat-model.md`). Connectors generalize the *kind* of secret (PAT, bot token, MCP server credential) and change none of the rules; envelope §7 already reserves exactly this ("Secret Store generalizes from provider API keys to credential kinds bound to grants"). A secret row: id, `credentialKind`, org binding, timestamps, fingerprint (last-4 or hash) for UI display. **No read path exists** — not for agents, not for the operator API, not in any artifact or log.

**How the runtime injects them: it doesn't — the proxy holds them.** The answer to "env at spawn?" is **no, never**. Two existing facts make env injection wrong: the sandbox env is a from-scratch whitelist precisely so a leaked env leaks only a revocable run token (`sandbox.md` §2), and subprocess isolation means anything in the sandbox must be assumed readable by a hostile agent (`cli-runtime.md` §8). So connector credentials follow the Tool Proxy path (envelope §3.4): agent calls a granted tool over its single MCP mount → proxy resolves the run token → checks grant + params → gates if governed → **decrypts the credential inside the control-plane process, attaches it to the upstream request, drops it** → ToolEvent → result. For MCP-backed connectors the credential goes to the executor connection the control plane itself holds (envelope §3.6: "launched/held by the control plane — NEVER inside a sandbox").

**The trust boundary, stated explicitly.** Everything sandbox-side of the control-plane API — the agent process, its workspace, its env, its generated session config — is *assumed compromised* for custody purposes. On the agent's side of the boundary exist: a run token (stored server-side only as a SHA-256 hash), tool schemas, and results. Connector credentials are never in the sandbox **at any tier** — which is strictly better than the CLI's own OAuth material under the §8 waiver, and worth stating plainly: connector credential hygiene does not wait for the docker tier.

**Hygiene at the boundary (server).** ToolEvents log a params *hash*, never raw params that could embed a token; proxy error paths scrub upstream error bodies (APIs echo bad credentials back); artifacts and stream-json transcripts never see a credential because the agent never had one to leak.

**Rotation.** Grants reference a secret **id**, never a value. The operator rotates via the write-only API; the next proxy call decrypts the new value. Zero session impact, zero agent awareness, no re-actuation — rotation is invisible below the boundary.

## 3. Least privilege — the ceiling enforced twice

A grant's ceiling is enforced at the Tool Proxy per call (**server**) and *again* in the upstream credential itself, so a proxy bug or platform compromise still cannot exceed what the credential permits. The credential is provisioned to match the grant, never the other way round.

**GitHub** (fine-grained PAT, or better a GitHub App installation — short-lived tokens, org-visible, revocable as a unit), for the worked example — a dedicated machine account, repository access **the Canopy repo only**:

| Canopy grant | Minimal upstream permission |
|---|---|
| `repo.read` (via `connector.github.repo.read`) | Metadata read (mandatory) + Contents **read** |
| `docs.repo.write` / `code.repo.write` | + Contents **read + write**. Branch scope (`canopy/*`) is proxy-enforced — PATs can't express it — mirrored upstream by branch protection on `main` |
| `connector.github.pr.create` (governed) | + Pull requests **read + write** |
| `repo.merge` (governed; not enabled in the example) | **none** — merge is human-ratified (`org-roadmap.md` §2, the recursion boundary); the agent-path credential should be *unable* to merge, with branch protection as the upstream twin of the ApprovalGate |
| Never | Administration, Actions/Workflows (a Contents-write PAT without the Workflows permission cannot alter `.github/workflows/` — keep it that way), Webhooks, anything org-level |

**Slack** (bot token, one workspace per org): `chat:write` (posts only to channels the bot is invited to — membership *is* the upstream allowlist), `channels:history` / `channels:read` for read grants. Never `chat:write.public`, `admin.*`, `users:read.email`. Slack scopes aren't per-channel, so the per-channel allowlist lives in grant params, proxy-enforced, with bot membership as the upstream ceiling.

**MCP servers:** no upstream scope vocabulary exists, so least privilege is manufactured platform-side — the pinned `toolSurface` exposes the minimal subset (01 §5); every exposed tool needs a curated grant with human-assigned `riskClass` and `governedActions` (`GRANT_UNCURATED` otherwise); and the credential the server itself wraps is minimally scoped at its own provider. An MCP server is exactly as trustworthy as its narrowest curation.

## 4. Revocation semantics and time-to-effect

The proxy checks **live** grant/binding/instance state per call (**server**) — the surface compiled into a session (`cli-runtime.md` §2) is UX, not the wall, so stale session configs don't extend authority:

| Lever | Mechanism | Time-to-effect |
|---|---|---|
| **Org kill switch** | disable the ConnectorInstance: every dependent grant fails closed at the proxy | immediate (next call, seconds) |
| Secret unbind / delete | next call fails the resolve step, 403, logged | immediate (next call) |
| Per-role / per-node ungrant | catalog or chart edit; proxy follows the live effective set; compiled session surface refreshes at next intake — until then the agent may *attempt* a removed tool and receive a logged 403 (envelope §3.3 layer 2) | next call |
| Running-session hard stop | engine halt flag → adapter interrupts at the turn boundary (`cli-runtime.md` §6) | ≤ one turn |
| **Upstream revocation** | revoke the PAT / uninstall the App / revoke the bot token | minutes — and independent of Canopy: works even if the control plane is what you distrust |

**The worked example's revocation drill.** Operator pulls the docs team's GitHub access: (1) disable `ci_gh_canopy` — next connector call from any session in the org 403s, fail-closed, logged; (2) optionally halt running sessions at the turn boundary; (3) revoke the PAT at GitHub; (4) if tearing down, deactuate: revoke run token → stop → destroy (`sandbox.md` §3 ordering). Nothing needs scrubbing in any workspace, artifact, or transcript — the raw token was never sandbox-side. Residual exposure: one in-flight upstream request completes; anything already published (a pushed branch) persists and is cleaned upstream by the operator — which is why outward-visible writes were governed in the first place.

## 5. Audit trail

Every connector invocation → ToolEvent: node, assignment, grant key, params hash, outcome, timestamp (envelope §3.4), extended with **connector instance id, upstream request id/URL, and intent id** — so any external effect chains back to *why* (assignment → brief → intent). Server-side records are authoritative over session-reported ones (`cli-runtime.md` §5). Append-only, exportable to a SIEM.

The worked example's one PR produces: the assignment + versioned brief tied to the intent; plan + stage updates; metered Steps for every model turn (SpendEvents in the ledger); ToolEvents for each `repo.read` fetch and each push to `canopy/docs/*`; ApprovalGate opened → operator resolution (identity + timestamp); the `create_pull_request` ToolEvent with the upstream PR URL; the deliverable artifact citing the branch/PR; meter close-out. GitHub-side, the branch name and machine-account authorship make provenance legible externally too. Every line of the PR is attributable to node + assignment + intent + approving human.

**Blast-radius statement — the acceptance test for the whole design.** A fully compromised agent session yields: a revocable run token, its own workspace, and the ability to *invoke* (not read the credentials of) its granted connectors within proxy-checked params, with governed actions still gated.
